## Findings

**F4 — "Changing a field makes the next submission a new payment request" (and the request form's `request-error` on a refused request);
regression from the new `change` listener in `forms/writeform.js`.** After a successful submit, the user edits a field and clicks
the submit button. The click is **lost**: no POST, no error, no success line.
Cause: `onEdit` now also runs on `change`, which fires when the edited input loses focus on mousedown on the button. It calls
`clearFeedback()`, which removes the success notice that sits in the slot **above** the button. The button jumps up before mouseup, so the
click never lands on it. Before U10 only `input` events cleared the slot (while typing), so nothing moved at click time.
Repro (A/B, same steps: bob requests 12.00 from ada, then changes the handle to `bob` and clicks Request money):
```
$PY reviews/stage2/tools/repro_u10_lost_click.py http://127.0.0.1:<port of 74d83a5>   # during-flight: posts 1, request-error 0, success 0
$PY reviews/stage2/tools/repro_u10_lost_click.py http://127.0.0.1:<port of 0259400>   # during-flight: posts 2, request-error 1
```
The analyst's `test_R2_PAY_5_*` fails the same way at both viewports. The same `writeForm` serves pay, authorize, split, request-row pay
and capture, so every form is exposed.
Expected: the click after an edit submits the edited form. For example, don't clear or reflow the slot on `change` (marking dirty is enough),
or keep the slot's height until the next submit.
