## Findings

**F1 — Stage 1 §10 "It must accept an unchanged export produced by this service" (with L8: snapshots are exported).** Every first
`GET /statement` stores the **whole window** (one row per entry) in `state.snapshots` until reset, and the export carries all of them. A wallet with
500 payments read 3000 times gives a 44 MB export; 5500 reads give **69.3 MB**. Its unchanged import is then refused, because the body exceeds
the 64 MiB import cap and the server closes the connection (client sees a broken pipe). A real client paging statements produces exports that this service can no longer import.
Repro: `python3 reviews/stage3/tools/snapshot_growth.py http://127.0.0.1:<port> 5500` → `export 200 size MB 69.3`, import → connection error.

**F2 — Stage 1 §2 limits "Memory 2 GiB" and §5 "Requests must not produce 5xx responses, including under concurrent load".** Memory grows linearly
with statement reads: 14 MiB → 216 MiB after 3000 reads → 382 MiB after 5500 (about 67 KB per read of a 500-entry window, at about 800 reads/s on 20
threads). Sustained statement reading reaches the 2 GiB limit within minutes, and the container is then OOM-killed.
Same repro (watch `docker stats`).

Direction (owner's choice): a snapshot can be **recomputed** instead of stored. Revisions are append-only with server-assigned `recorded_at`, so
freezing (user, from, to-or-N, effective known instant = min(known_at, N), known_at echo) is enough. Selecting revisions recorded ≤ that
instant reproduces exactly the same entries and balances later. That makes each snapshot O(1) in memory and in the export.

(above); F1/F2 are a storage design issue.
