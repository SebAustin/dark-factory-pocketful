## Findings

**F7 — §2 "Per-request timeout | 5 s", "Concurrent requests | up to 50 in flight" (regression).**
`_HASH_SLOT = BoundedSemaphore(1)` serialises every interactive scrypt onto one of the two vCPUs, so a burst of
50 auth calls takes about 50 × the single-hash time. On this host one n=2^14 scrypt measured 104 ms inside the container, so the
tail crosses 5 s. A/B under the same host load (load average about 16), 3 runs each, `python3 reviews/stage1/tools/burst_auth.py http://localhost:<port>`:

| build | signup max | login max | calls > 5 s |
|---|---|---|---|
| 2b73788 (before S1.13) | 3.95 / 3.54 / 3.46 s | 3.13 / 2.86 / 3.42 s | 0 / 0 / 0 |
| 5ff293a (S1.13) | 5.86 / 5.08 / 5.90 s | 4.76 / 4.40 / 5.54 s | 9 / 3 / 14 |

An earlier single run on 5ff293a, right after `soak.py big`, gave signup max 7.24 s and login max 7.74 s.
Expected: every call within 5 s with 50 in flight. The S1.13 goal itself says "every call answers within 5 s under 50 in
flight with signup/login in the mix".
Direction (owner's choice): size the slot to the CPU quota (2 slots for 2 vCPU keeps total CPU at or under quota, so no
throttling, at half the queue). The before-build throttled heavily (nr_throttled 207 of 220) because it ran unbounded.
Also consider whether n=2^14 is needed for the budget.
