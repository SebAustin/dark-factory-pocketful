## Outside this item's scope: new blocking findings from the committed acceptance suite

At 2b73788, `TARGET_URL=http://127.0.0.1:18409 python -m pytest stage-1/acceptance -q` →
**3 failed, 385 passed, 3 skipped, 9 errors**. The 9 errors happened because the container had died. I reproduced each failure by hand
on a fresh container:

**F4 — R-5.19 §5 "Requests must not produce 5xx responses" (service crash).** A body nested 100000 levels deep
(`b"[" * 100000 + b"]" * 100000`) POSTed to /payments kills the process: the container exits with code **139 (SIGSEGV)**, and every
later request fails with a connection reset. Depth 1000 is handled (400). The likely cause is the C JSON scanner recursing on a request
thread, whose default stack on Alpine/musl is small, before Python's recursion limit can trigger. Owner: `app/http_util.py`
(S1.1, builder). Repro: the probe in `stage-1/acceptance/test_zz_crash_probes.py`, then
`docker inspect <c> --format '{{.State.ExitCode}}'` → 139.

**F5 — R-5.19 / R-4.23 / per-request timeout 5 s (service wedge).** `{"to_handle":"b","amount":1e999999999}` on
/payments never answers, and `/health` times out afterwards: the whole service hangs. The likely cause is that `validation.integral` calls
`int(Decimal("1e999999999"))`, building a billion-digit integer while the route holds `STORE.lock`. Expected: 422
validation_failed, fast. Owner: `app/validation.py` (S1.3, builder). Repro:
`curl -m 8 -X POST :PORT/payments -H 'Authorization: Bearer $T' -H 'Idempotency-Key: y' -d '{"to_handle":"b","amount":1e999999999}'`.

**F6 — R-4.23 / §5 "invalid `amount` values … are 422 `validation_failed`".** A 5001-digit integer literal amount
(`1` followed by 5000 zeros) → **400** malformed_request "body is not valid JSON". The body is valid JSON; Python's
4300-digit int-parsing limit makes `json.loads` raise. Expected: 422. Owner: `app/http_util.py` (builder). Repro: acceptance
`test_payments.py::test_R8_7_R4_23_amount_bounds[1000…-False]`.
