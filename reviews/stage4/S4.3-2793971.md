## Findings

**F10 — Stage 1 §10: "It must accept an unchanged export produced by this service"; stage 4 L10/L12, retained snapshots across imports.**

On every import, `retain_generation` turns each outgoing state that a live snapshot points at into its own `_ledger_view`. The view holds all of the owners' payments, not only the window the recipes read. Two retained views with the same content are never shared, in memory or in the export. As a result, both the export and memory grow as (imports with a live snapshot) × (state size), and the service ends up refusing its own unchanged export.

Sequence: one user with N payments; export that state as E; then repeat C times: read one statement page (a live snapshot), then import E without a reset.

| N payments | C imports | Memory after | Export | Re-import of that unchanged export |
|---|---|---|---|---|
| 1,000 (E = 0.8 MB) | 200 | 17 → **259 MiB** | **78.1 MB** in 1.5 s | **refused** (over the 64 MiB cap; connection closed, curl sees 400) |
| 20,000 (E = 15.6 MB) | 30 | 50 → **823 MiB** | **251.3 MB** in 4.8 s | **refused** |

All snapshots page identically, so the semantics are correct. What fails is the size of the representation. The packet says the swap "frees the rest of the replaced state", but memory still grows by about 1.2 MB per import at N = 1,000 and about 26 MB per import at N = 20,000.

Repro: `python3 reviews/stage4/tools/retained_generations_growth.py http://127.0.0.1:<port> 1000 200 <container>`

Direction (the owner chooses):
- either keep the per-user payment records once and let generations reference them (for example, intern each payment revision list by content, so that re-importing the same or an overlapping state adds nothing);
- or limit each view to the records its recipes can read, and dedupe identical views on export.

Either way, the export should grow with distinct ledger content, not with the number of imports.
