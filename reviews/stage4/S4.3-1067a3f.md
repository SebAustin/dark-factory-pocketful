## Findings

**F10 (still open) — Stage 1 §10: "It must accept an unchanged export produced by this service" (L10/L12 retained snapshots).** The direction given in the previous review: "the export should grow with distinct ledger content, not with the number of imports".

Identical imports are now shared, but **distinct** generations are not. Each distinct view still carries its own full index:
- `payments`: payment id → 64-hex digest;
- `user_payments` lists, one entry per payment the owner has ever had.

So a generation costs about 85 bytes per payment in the state, both in the export and in memory, even when it differs from the previous generation by a single payment.

Sequence (`--drift`): before each read, make one payment, so each replaced state is E plus one more payment; then import E without a reset; repeat. The distinct ledger content grows by 30 payment records, yet the export grows by 50 MB:
- export goes from 26.1 to **76.0 MB**;
- the re-import of that unchanged export is **refused**.

Repro: `python3 reviews/stage4/tools/retained_generations_growth.py http://127.0.0.1:<port> 20000 30 <container> --drift`

Direction (the owner chooses): share the index structure as well as the records. For example:
- intern the per-user id lists in fixed-size chunks by digest, or represent a generation as a base view plus a delta;
- or limit each view to the payments its recipes' windows can read, and derive `user_payments` from the records instead of storing it.

Either way, a generation that adds k payments to a shared one should cost O(k), not O(state).
